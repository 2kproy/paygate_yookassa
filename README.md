# paygate_yookassa

Автономный платёжный релей для ЮKassa. Ставится рядом с сайтом-**агрегатором** и
проксирует платежи между **суб-мерчантом** (внешний сервис, чьи платежи
проводятся) и кассой ЮKassa агрегатора.

```
Создание:  суб-мерчант ──HMAC──▶ paygate ──ключ ЮKassa──▶ api.yookassa.ru
Вебхук:    api.yookassa.ru ──▶ paygate ──очередь+HMAC──▶ суб-мерчант
Возврат:   ЮKassa ──▶ paygate /pay/return?id=<токен> ──302──▶ origin суб-мерчанта (или заглушка)
```

**Зачем.** Требование кассы — все обращения к ЮKassa с домена/IP агрегатора.
paygate это обеспечивает: ключ ЮKassa живёт только здесь, исходящие вызовы идут
с его хоста, вебхуки приходят сюда. Суб-мерчант общается только с paygate по
HMAC — свой ключ ЮKassa он не держит.

Один сервис = один агрегатор. Для другого агрегатора — поднять копию на его
сервере со своим `.env.prod` (см. «Переносимость»).

---

## Как это защищено

- **Подделать «оплачено» нельзя.** Тело вебхука ЮKassa не подписывает —
  поэтому решение об оплате принимает суб-мерчант **перепросом статуса**
  `GET /agg/v1/payments/{id}` (проксируется в ЮKassa с ключом). Форвард вебхука
  — лишь триггер: даже подделав его, атакующий не подделает ответ ЮKassa.
- **Вход ЮKassa → paygate**: IP-allowlist сетей ЮKassa.
- **Вход суб-мерчант → paygate**: HMAC-подпись тела + метка времени
  (анти-replay ±5 мин) + опциональный IP-allowlist.
- **Форвард paygate → суб-мерчант**: HMAC-подпись, суб-мерчант проверяет.
- **Надёжность**: вебхук персистится в SQLite и подтверждается ЮKassa `200`
  сразу, затем доставляется суб-мерчанту из очереди с ретраями/бэкоффом и
  dead-letter — двойной хоп не теряет платежи. Порядок событий неважен:
  суб-мерчант всё равно перепрашивает актуальный статус.
- **Метаданные не утекают**: суб-мерчант кладёт свои `metadata` как обычно —
  paygate заменяет их непрозрачным `ref` перед отправкой в ЮKassa и
  **восстанавливает оригинал на обратном пути** (вебхук, перепрос статуса,
  ответ создания). Касса видит только `ref`; суб-мерчант получает свои
  metadata без изменений.
- **Редирект**: токен случайный (не payment_id), живёт только для реального
  платежа; после успеха — ещё `SUCCESS_TTL_SECONDS`, иначе до конца жизни
  платежа. Неизвестный/просроченный → заглушка. Origin проверяется по
  allowlist (анти-open-redirect).

## Быстрый старт (тот же домен, разные пути)

1. `cp .env.example .env.prod` и заполнить (см. таблицу ниже).
2. Узнать docker-сеть Caddy сайта-агрегатора: `docker network ls`. Задать
   `CADDY_NETWORK=<имя_сети>` (env для compose или прямо в `docker-compose.yml`).
3. `docker compose up -d --build`.
4. В `Caddyfile` сайта вставить блок из `Caddyfile.snippet` (первым в блоке
   домена агрегатора) и перезагрузить Caddy
   (`docker exec <caddy-контейнер> caddy reload --config /etc/caddy/Caddyfile`).
5. В кабинете ЮKassa вебхук указать на
   `https://<домен-агрегатора>/bff/v1/billing/webhook/yookassa`, события:
   `payment.succeeded`, `payment.waiting_for_capture`, `payment.canceled`,
   `payment_method.active`, `refund.succeeded`.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `PUBLIC_URL` | Публичный адрес сервиса (домен агрегатора). |
| `YOOKASSA_SHOP_ID` / `YOOKASSA_SECRET_KEY` | 🔑 Касса агрегатора. Живут только здесь. |
| `YOOKASSA_WEBHOOK_IPS` | Сети вебхуков ЮKassa (дефолт заполнен). |
| `WEBHOOK_PATH` | Путь вебхука (совпадает с настройкой в кабинете). |
| `INGRESS_SECRET` | 🔑 HMAC-секрет: суб-мерчант → paygate. |
| `INGRESS_ALLOWED_IPS` | IP серверов суб-мерчанта (CIDR). |
| `FORWARD_URL` | Вебхук-эндпоинт суб-мерчанта (куда форвардим). |
| `FORWARD_SECRET` | 🔑 HMAC-секрет: paygate → суб-мерчант. |
| `ALLOWED_RETURN_ORIGINS` | Разрешённые origin'ы возврата (все домены суб-мерчанта). |
| `REDIRECT_TTL_SECONDS` / `SUCCESS_TTL_SECONDS` | Жизнь токена редиректа. |
| `DB_PATH` | Файл SQLite (volume). |

🔑 — секреты. `INGRESS_SECRET` и `FORWARD_SECRET` должны совпадать с теми, что
задаёт суб-мерчант на своей стороне.

## Эндпоинты

`/agg/v1/*` — зеркало `/v3/*` ЮKassa (принимает те же тела):
- `POST /agg/v1/payments` — создать платёж или автосписание (`payment_method_id`).
- `GET  /agg/v1/payments/{id}` — статус платежа (перепроверка).
- `POST /agg/v1/refunds` — возврат.

Служебные:
- `POST <WEBHOOK_PATH>` — вебхук ЮKassa (публичный, IP-allowlist).
- `GET  <RETURN_PATH>?id=<токен>` — возврат пользователя (302 или заглушка).
- `GET  /healthz`.

## Интеграция: что поменять в существующем ЮKassa-клиенте суб-мерчанта

paygate — прозрачный прокси: **тела запросов остаются обычными телами ЮKassa**.
Меняется только адрес, авторизация и подпись. Три изменения:

### 1) Исходящие запросы (create / charge / refund / get)

- Базовый адрес клиента: `https://api.yookassa.ru/v3` → `https://<домен-агрегатора>/agg/v1`.
- **Убрать Basic-Auth** (`shopId:secretKey`) — ключ подставит paygate.
- Добавить к каждому запросу HMAC-подпись **над теми же байтами, что уходят в тело**:

```
ts = <unix seconds>
X-Timestamp: ts
X-Signature: hex( HMAC_SHA256( INGRESS_SECRET, ts + "." + rawBody ) )
Idempotence-Key: <как и раньше>   # для POST; пробрасывается в ЮKassa как есть
```

Для `GET` тело пустое → подпись считается над `ts + "."` (пустой rawBody).
⚠️ Подписывайте ИМЕННО те байты, что отправляете (не пересобирайте JSON после
подписи), иначе подпись не сойдётся.

`confirmation.return_url` стройте как обычно (свою страницу возврата) — paygate
сам перепишет его на свой токен-редирект, а ваш URL сохранит как цель. Ваши
домены возврата должны быть в `ALLOWED_RETURN_ORIGINS`.

### 2) Приём вебхука

paygate шлёт на `FORWARD_URL` **сырое тело ЮKassa дословно** (с восстановленными
metadata). Вместо старой проверки IP ЮKassa — проверяйте подпись:

```
X-Paygate-Timestamp: ts
X-Paygate-Signature:  hex( HMAC_SHA256( FORWARD_SECRET, ts + "." + rawBody ) )
```

Дальше — как раньше: статус берите перепросом `GET /agg/v1/payments/{id}`
(через paygate), а не из тела.

🔴 **Отвечайте `200` на события, которые не обрабатываете**
(`payment_method.active`, `refund.*`, `waiting_for_capture`). `4xx/5xx`
заставляют paygate ретраить и в итоге бросить в dead-letter — их оставляйте
ТОЛЬКО для «повтори позже» (транзакция ещё не записана / касса недоступна).

### 3) metadata — менять НЕ нужно

Кладите и читайте `metadata` как раньше. paygate прячет их от ЮKassa и
восстанавливает оригинал в вебхуке/перепросе статуса сам.

### Откат

Всё включается наличием секрета/адреса paygate на стороне суб-мерчанта. Уберёте
их (вернёте прямой адрес ЮKassa + Basic-Auth + проверку по IP) — работает
по-старому.

## Что видит ЮKassa (и что нет)

| Поле | Что уходит в ЮKassa |
|---|---|
| Исходящий IP | Хост агрегатора (paygate) |
| `return_url` | Домен агрегатора (`/pay/return`) — редирект дальше невидим кассе |
| `metadata` | Только непрозрачный `ref` |
| `description` / чек | То, что прислал суб-мерчант; фискализация — под юрлицом агрегатора |

Идентифицирующих полей суб-мерчанта в объекте платежа не остаётся. Остаётся
неустранимое: поведенческий паттерн (суммы, периодичность, доля рекуррентов).

## Эксплуатация

- Хранилище — SQLite (`DB_PATH`, volume): `redirect_token`, `webhook_delivery`
  (очередь), `payment_meta` (маппинг metadata). Уборка старых строк — автоматом.
- Не доставленные вебхуки после `RELAY_MAX_ATTEMPTS` помечаются `dead=1` в
  `webhook_delivery` (лог `[relay] DEAD ...`) — повод для алерта/сверки.
- Сервис не публикуется наружу (`expose`, не `ports`) — доступ только через
  Caddy; поэтому его заголовкам (X-Real-IP) можно доверять.

## Переносимость

Копия под другого агрегатора: клонировать репозиторий на его сервер, задать свой
`.env.prod` (своя касса, свои секреты, свой `FORWARD_URL`), врезать
`Caddyfile.snippet` в его Caddy. Кода менять не нужно.
